# 🍿 Watch Together
 
Веб-приложение для совместного просмотра YouTube с синхронизацией в реальном времени. Один человек создаёт комнату, отправляет ссылку другу, и дальше оба смотрят одно и то же видео: пауза, перемотка и смена ролика у одного мгновенно повторяются у второго.
 
**Демо: https://watch-together-murex.vercel.app/**
 
> ⏳ **Важно: сервер может «просыпаться» до минуты.**
> Сервер сигналинга размещён на бесплатном тарифе Render и засыпает после простоя. Если вы заходите первым за долгое время, создание комнаты и первое подключение могут занять **до минуты**, а в интерфейсе появится подсказка «Сервер просыпается». Если подключение не удалось с первого раза, нажмите «Повторить» или обновите страницу. Дальше всё работает быстро.
 
## Как попробовать за 1 минуту
 
1. Откройте демо и вставьте ссылку на любое видео YouTube (подойдёт обычное видео, у которого автор не запретил встраивание).
2. Нажмите «Создать комнату» и скопируйте ссылку-приглашение.
3. Откройте её в другой вкладке, браузере или на телефоне и нажмите «Присоединиться к просмотру».
4. Поставьте видео на паузу, перемотайте его или смените ссылку: у второго участника всё повторится.
## Возможности
 
- Создание комнаты по ссылке на YouTube, приглашение по персональной ссылке
- Комната на двух участников, третий получает понятное сообщение «Комната занята»
- Синхронизация play, pause, перемотки (в том числе на паузе) и смены видео в обе стороны
- Управление равноправное: любой участник может нажать паузу, перемотать или сменить видео
- Автоматическая коррекция дрейфа: хост раз в 5 секунд отправляет позицию, и отставший участник подтягивается
- Статус подключения и участников в реальном времени, определение выхода партнёра (в том числе при закрытии вкладки)
- Автоматическое переподключение к серверу сигналинга при его перезапуске
- Работа из разных сетей, включая мобильный интернет, благодаря TURN-серверу
- Адаптивный интерфейс, светлая и тёмная темы
## Как это устроено
 
Видео не проходит через наш сервер: каждый браузер загружает его напрямую с YouTube. Между участниками передаются только маленькие сообщения о состоянии плеера, и идут они **напрямую между браузерами** по WebRTC DataChannel. Своей базы данных и бэкенда с логикой комнат у проекта нет.
 
```
Браузер A  ◄─────── WebRTC DataChannel ───────►  Браузер B
    │        (play / pause / seek / heartbeat)        │
    │                                                 │
    └──────► Сервер сигналинга (PeerJS, Render) ◄─────┘
             только знакомит участников друг с другом
                          +
             STUN / TURN (Metered) для прохода через NAT
```
 
**Комната** это peer id хоста, который регистрируется на сервере сигналинга. Ссылка-приглашение содержит этот id, а когда хост закрывает вкладку, комната перестаёт существовать.
 
### Что пришлось решить
 
- **Эхо-события.** Когда плеер программно ставится на паузу по команде партнёра, он сам порождает событие паузы, и без защиты участники бесконечно пересылали бы друг другу одно и то же. Решено через ожидаемое состояние плюс короткие окна игнорирования.
- **Нет события «перемотка».** YouTube IFrame API не сообщает о перемотке, поэтому позиция опрашивается и сравнивается с ожидаемой, с разными порогами для воспроизведения и паузы.
- **Дрейф воспроизведения.** Буферизация, сеть и фоновые вкладки разводят плееры. Хост периодически отправляет снимок состояния, а гость корректирует позицию только при заметном расхождении и совпадающем состоянии play/pause.
- **Политика автовоспроизведения браузеров.** Гость без действия на странице не может запустить видео, поэтому перед входом показывается кнопка «Присоединиться».
- **Фоновые вкладки.** Скрытая вкладка замораживает плеер. При возврате на вкладку клиент запрашивает у партнёра актуальное состояние и временно глушит ложные события.
- **Обнаружение выхода партнёра.** Закрытие вкладки не всегда приводит к событию в WebRTC, поэтому добавлены прощальное сообщение и проверка «жив ли партнёр» по пингам.
- **Бесплатный хостинг.** Холодный старт сервера смягчён «прогревом», подсказкой пользователю, автоповтором подключения и переподключением хоста к серверу после его перезапуска.
## Технологии
 
| Область | Что использовано |
|---|---|
| Фронтенд | React, TypeScript, Vite |
| Интерфейс | Tailwind CSS, shadcn/ui, lucide-react, sonner |
| Маршрутизация | React Router |
| Видео | YouTube IFrame Player API (react-youtube) |
| Реалтайм | WebRTC (DataChannel) через PeerJS |
| Сигналинг | Собственный `peer` (PeerJS server) на Node.js |
| NAT traversal | публичные STUN, TURN от Metered |
| Деплой | Vercel (фронтенд), Render (сервер сигналинга) |
 
## Структура проекта
 
```
src/
  pages/
    HomePage/        создание комнаты
    RoomPage/        комната: плеер, статус, сборка хуков
  hooks/
    usePeerRoom.ts   соединение: роли, лимит участников, живость партнёра, переподключение
    usePlayer.ts     плеер: снимок состояния, применение чужих команд, детектор перемотки, heartbeat
    useSlowHint.ts   подсказка при долгом подключении
  components/        StatusBadge, CopyLink, ChangeVideoForm, ui/ (shadcn)
  lib/
    parseYoutubeUrl.ts   извлечение id видео из разных форматов ссылок
    roomId.ts            генерация id комнаты
    iceServers.ts        STUN/TURN-конфигурация
    peerOptions.ts       параметры подключения к серверу сигналинга
    warmUp.ts            «прогрев» бесплатного сервера
    types.ts             типы состояния плеера и сообщений
```
 
## Запуск локально
 
Нужны Node.js и yarn.
 
```bash
git clone <адрес репозитория>
cd watch-together
yarn
cp .env.example .env     # заполните переменные, см. ниже
yarn dev
```
 
### Переменные окружения
 
| Переменная | Назначение |
|---|---|
| `VITE_PEER_HOST` | адрес сервера сигналинга (например, `localhost` локально) |
| `VITE_PEER_PORT` | порт (`9000` локально, `443` в продакшене) |
| `VITE_PEER_PATH` | путь, `/` |
| `VITE_PEER_SECURE` | `true` для HTTPS/WSS, `false` локально |
| `VITE_TURN_URLS` | адреса TURN через запятую (необязательно) |
| `VITE_TURN_USERNAME` | логин TURN (необязательно) |
| `VITE_TURN_CREDENTIAL` | пароль TURN (необязательно) |
 
Без TURN приложение работает, но у части пользователей (строгие NAT, корпоративные сети) соединение может не установиться.
 
### Сервер сигналинга
 
Отдельный маленький проект: репозиторий `watch-together-signaling` (Node.js + пакет `peer`, один файл). Локально:
 
```bash
yarn start    # слушает порт 9000
```
 
## Ограничения
 
- Комната живёт, пока открыта вкладка хоста, ссылка после закрытия вкладки хоста перестаёт работать
- Максимум два участника
- Некоторые видео нельзя встроить (запрет автора): приложение сообщает об этом
- Скорость воспроизведения и конец видео не синхронизируются
- Бесплатные хостинги и тариф TURN ограничивают доступность и объём трафика
## Идеи для развития
 
- Чат между участниками поверх уже открытого канала
- Голосовая связь через WebRTC
- Комнаты на несколько человек и очередь видео
- Автоматическое переподключение гостя после перезагрузки хоста
- Тесты на ключевую логику синхронизации
## Что показывает этот проект
 
Реалтайм-взаимодействие в браузере без классического бэкенда (WebRTC, сигналинг, NAT traversal), работа со сторонним API со сложным поведением (YouTube IFrame), проектирование надёжной синхронизации состояния (идемпотентность, защита от гонок и эха, обработка обрывов), TypeScript и React-хуки с аккуратным управлением состоянием, а также полный путь до продакшена: деплой фронтенда и сервера, переменные окружения, работа с ограничениями бесплатных тарифов.
